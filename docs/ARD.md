## ADR-001 — Единый Node.js бэкэнд для всех клиентов

**Дата:** Май 2026  
**Статус:** Accepted

### Контекст

Приложение имеет два клиента: Web (React) и iOS (Swift). В будущем планируется macOS. Все клиенты должны иметь доступ к одним данным (история чатов, API-ключи), а также проксировать запросы к LLM-провайдерам.

### Решение

Один бэкэнд на Node.js + TypeScript, общий для всех клиентов. Клиенты общаются с ним по REST + SSE.

```
Web (React)  ──┐
               ├──▶  Node.js Backend  ──▶  LLM APIs
iOS (Swift)  ──┘
```

### Обоснование

- **CORS на Web:** браузер не может напрямую обращаться к большинству LLM API — они блокируют cross-origin запросы. Бэкэнд решает это полностью.
- **Синхронизация:** история чатов и ключи доступны с любого устройства.
- **Единая точка интеграции:** новый провайдер добавляется один раз на бэкэнде, а не в каждом клиенте.
- **Безопасность:** API-ключи пользователей не хранятся в браузере или на устройстве.
- **Node.js:** TypeScript-стек одинаковый для Web-фронта и бэкэнда, единая команда, общие типы через shared пакет.

### Отклонённые альтернативы

| Альтернатива | Причина отклонения |
|---|---|
| Клиент напрямую к LLM API | CORS блокирует запросы из браузера у большинства провайдеров |
| Отдельный бэкэнд для Web и iOS | Дублирование кода, сложнее поддерживать синхронизацию данных |
| Python / Go бэкэнд | Команда работает на TypeScript, переключение контекста замедляет разработку |
| BaaS (Supabase Edge Functions) | Ограниченный контроль над логикой проксирования и стримингом |

### Последствия

- Бэкэнд становится единой точкой отказа — нужен мониторинг и health checks
- Требует деплоя и поддержки сервера (Railway / Fly.io)
- Все клиенты зависят от доступности бэкэнда

## ADR-002 — Бизнес-модель BYOK: ключи хранятся на сервере в зашифрованном виде

**Дата:** Май 2026  
**Статус:** Accepted

### Контекст

Бизнес-модель — BYOK (Bring Your Own Key): пользователь использует собственные API-ключи к провайдерам. Вопрос: где хранить ключи — только на клиенте или на сервере?

### Решение

Ключи хранятся на сервере в зашифрованном виде (см. ADR-007). Клиент никогда не получает сам ключ — только статус его наличия.

### Обоснование

- **Синхронизация между устройствами:** пользователь вводит ключ один раз, он работает на Web и iOS без повторного ввода.
- **Безопасность клиента:** ключ не лежит в localStorage браузера или в файловой системе iOS, откуда его легче достать.
- **UX:** не нужно вводить ключи заново при смене устройства или очистке браузера.

### Отклонённые альтернативы

| Альтернатива | Причина отклонения |
|---|---|
| Хранить только на клиенте (localStorage / Keychain) | Нет синхронизации между устройствами, плохой UX |
| Хранить на клиенте + ручной экспорт/импорт | Ненадёжно, неудобно, пользователи теряют ключи |
| Мы покупаем API и берём деньги с пользователей | Иная бизнес-модель, требует платёжной системы и управления расходами |

### Последствия

- Требует надёжного шифрования на сервере (AES-256-GCM, per-user ключи)
- Ответственность за безопасность ключей лежит на нас
- При компрометации сервера ключи защищены шифрованием, но риск не нулевой — нужна политика раскрытия инцидентов

## ADR-003 — Hono как HTTP-фреймворк для бэкэнда

**Дата:** Май 2026  
**Статус:** Accepted

### Контекст

Нужен HTTP-фреймворк для Node.js бэкэнда. Требования: TypeScript из коробки, поддержка стриминга (SSE), высокая производительность, активная поддержка.

### Решение

Используем **Hono** — современный ultrafast веб-фреймворк с первоклассной поддержкой TypeScript и Web Standards API.

### Обоснование

- **Web Standards:** Hono работает на стандартных Request/Response объектах — код легко переносится на edge (Cloudflare Workers, Deno Deploy) в будущем.
- **TypeScript:** полная типизация из коробки, включая типизированные роуты и middleware.
- **SSE:** встроенная поддержка `streamSSE` — не нужны сторонние библиотеки.
- **Производительность:** значительно быстрее Express по бенчмаркам на простых роутах.
- **Размер:** минимальные зависимости, нет legacy-кода.

### Сравнение фреймворков

| Критерий | Hono | Express | Fastify | NestJS |
|---|---|---|---|---|
| TypeScript out-of-box | ✅ | ❌ (типы отдельно) | ✅ | ✅ |
| SSE поддержка | ✅ встроена | ❌ вручную | ⚠️ плагин | ⚠️ плагин |
| Web Standards API | ✅ | ❌ | ❌ | ❌ |
| Edge-ready | ✅ | ❌ | ❌ | ❌ |
| Размер / простота | ✅ минимальный | ⚠️ много legacy | ✅ | ❌ тяжёлый |
| Экосистема / зрелость | ⚠️ молодой | ✅ огромная | ✅ зрелый | ✅ enterprise |

### Отклонённые альтернативы

- **Express:** устаревший подход, нет нативного TypeScript, SSE требует ручной работы
- **Fastify:** хорош, но не Web Standards, SSE через плагин
- **NestJS:** избыточен для нашего случая, тяжёлый boilerplate, медленнее старт разработки

### Последствия

- Hono относительно молодой — меньше готовых решений в Stack Overflow, но документация хорошая
- При необходимости перехода на edge-деплой (Cloudflare Workers) изменения минимальны

## ADR-004 — Стриминг ответов через SSE, не WebSocket

**Дата:** Май 2026  
**Статус:** Accepted

### Контекст

LLM-провайдеры отдают ответы токен за токеном. Нужен механизм передачи этого стрима от бэкэнда к клиентам в реальном времени.

### Решение

Используем **Server-Sent Events (SSE)** для стриминга ответов от бэкэнда к клиентам.

```
LLM API  ──SSE──▶  Node.js Backend  ──SSE──▶  Web / iOS Client
```

### Обоснование

- **Однонаправленность:** стриминг LLM — это всегда сервер → клиент. SSE создан именно для этого.
- **Простота:** SSE работает поверх обычного HTTP, не требует upgrade соединения.
- **Браузерная поддержка:** нативный `EventSource` API во всех современных браузерах, автоматический reconnect.
- **iOS:** `URLSession` с async/await нативно поддерживает SSE через `bytes(for:)`.
- **Совместимость с провайдерами:** OpenAI, Anthropic, Google — все используют SSE. Бэкэнд просто пробрасывает тот же формат.
- **Инфраструктура:** SSE проходит через стандартные HTTP-прокси и CDN без дополнительной настройки.

### Отклонённые альтернативы

| Альтернатива | Причина отклонения |
|---|---|
| WebSocket | Двунаправленный протокол избыточен для однонаправленного стрима; сложнее в инфраструктуре (прокси, балансировщики) |
| Long polling | Высокая задержка, неэффективно, устаревший подход |
| HTTP chunked (без SSE) | Нет стандартного формата событий, нет автоматического reconnect |

### Последствия

- SSE не поддерживает бинарные данные — для передачи файлов используется обычный POST
- При использовании HTTP/1.1 лимит на 6 соединений на домен может стать проблемой при 4+ параллельных стримах в мультимодельном режиме — решается HTTP/2 (multiplexing)
- Необходимо настроить таймауты на прокси/nginx чтобы не разрывать длинные SSE-соединения

## ADR-005 — Единый Provider Adapter Interface для всех LLM

**Дата:** Май 2026  
**Статус:** Accepted

### Контекст

Приложение работает с 5+ провайдерами (OpenAI, Anthropic, Google, Mistral, Groq, Ollama), у каждого свой API. Нужна архитектура, которая изолирует различия и позволяет добавлять новых провайдеров без изменения бизнес-логики.

### Решение

Паттерн **Adapter**. Каждый провайдер реализует единый интерфейс `LLMProvider`. Вся бизнес-логика работает только с этим интерфейсом.

```typescript
interface LLMProvider {
  id: string
  name: string
  models(): Promise<Model[]>
  chat(request: ChatRequest): Promise<ChatResponse>
  stream(request: ChatRequest): AsyncIterable<StreamChunk>
}

interface ChatRequest {
  model: string
  messages: Message[]
  systemPrompt?: string
  temperature?: number
  maxTokens?: number
}

interface StreamChunk {
  delta: string
  finishReason?: 'stop' | 'length' | 'error'
  usage?: TokenUsage
}
```

### Структура провайдеров

```
src/providers/
├── base.ts              # LLMProvider interface + общие типы
├── registry.ts          # Реестр провайдеров, выбор по ID
├── openai.ts            # OpenAI + OpenAI-compatible (Mistral, Groq)
├── anthropic.ts         # Anthropic Messages API
├── google.ts            # Gemini API
└── ollama.ts            # Ollama local
```

### Обоснование

- **Изоляция:** добавление нового провайдера — создать один файл, реализовать интерфейс, зарегистрировать в registry.
- **Тестируемость:** можно мокировать интерфейс в тестах без реальных API-запросов.
- **OpenAI-compatible:** Mistral, Groq, Together и многие другие совместимы с OpenAI API — один адаптер закрывает сразу несколько провайдеров через конфигурацию базового URL.

### Последствия

- Нормализация форматов сообщений (например, Anthropic не поддерживает `system` внутри `messages`) — решается внутри адаптера
- Различия в поддерживаемых параметрах (не все модели поддерживают `top_p`, `presence_penalty`) — адаптер фильтрует неподдерживаемые параметры

## ADR-006 — PostgreSQL + Drizzle ORM как слой данных

**Дата:** Май 2026  
**Статус:** Accepted

### Контекст

Нужна реляционная БД для хранения пользователей, чатов, сообщений и зашифрованных ключей. Нужен ORM с хорошей поддержкой TypeScript.

### Решение

**PostgreSQL** как база данных, **Drizzle ORM** как типобезопасный слой доступа к данным.

### Обоснование выбора PostgreSQL

- Реляционная модель хорошо подходит для чатов (users → chats → messages)
- JSON/JSONB колонки для хранения гибких метаданных (настройки модели, метаданные сообщений)
- Зрелость, надёжность, широкая поддержка у хостинг-провайдеров

### Обоснование выбора Drizzle

- **TypeScript-first:** схема описывается в TypeScript, типы генерируются автоматически — нет расхождения между схемой и типами
- **SQL-like API:** запросы читаются как SQL, нет магии и непредсказуемого поведения как у Prisma
- **Производительность:** нет runtime overhead как у Prisma (генерация запросов, отдельный engine процесс)
- **Migrations:** встроенный `drizzle-kit` для управления миграциями

### Сравнение ORM

| Критерий | Drizzle | Prisma | TypeORM | Kysely |
|---|---|---|---|---|
| TypeScript-first | ✅ | ✅ | ⚠️ | ✅ |
| Производительность | ✅ высокая | ⚠️ overhead | ⚠️ | ✅ |
| SQL-контроль | ✅ прямой | ❌ абстрагирован | ⚠️ | ✅ |
| Миграции | ✅ | ✅ | ⚠️ | ❌ нет |
| Зрелость | ⚠️ молодой | ✅ зрелый | ✅ | ⚠️ |

### Последствия

- Drizzle молодой — некоторые edge-cases могут потребовать raw SQL
- Для деплоя нужен управляемый PostgreSQL (Railway Postgres, Supabase, Neon)
- При росте нагрузки на чтение истории — партиционирование таблицы `messages` по `chat_id`

## ADR-007 — Шифрование API-ключей: AES-256-GCM с per-user ключом

**Дата:** Май 2026  
**Статус:** Accepted

### Контекст

API-ключи пользователей хранятся на нашем сервере. Если БД скомпрометирована, ключи не должны быть читаемы. При этом бэкэнд должен уметь расшифровать ключ для проксирования запроса.

### Решение

Двухуровневое шифрование:

```
User Password  ──PBKDF2──▶  User Encryption Key (UEK)
UEK  ──AES-256-GCM──▶  Encrypted API Key
Encrypted API Key  ──▶  PostgreSQL (хранится)

При запросе:
JWT Token  ──▶  User ID  ──▶  UEK из памяти/кэша  ──▶  Decrypt API Key  ──▶  LLM Request
```

**Детали реализации:**

- Алгоритм: AES-256-GCM (аутентифицированное шифрование, защита от подмены)
- KDF: PBKDF2 с SHA-256, 100 000 итераций, соль — per-user random 32 байта
- UEK: не хранится в БД. Деривируется из пароля при логине и кэшируется в памяти сервера на время сессии (или хранится зашифрованным в Redis с TTL)
- Каждый зашифрованный ключ содержит: `iv` (12 байт) + `authTag` (16 байт) + `ciphertext`

### Обоснование

- **AES-256-GCM:** стандарт де-факто, аутентифицированное шифрование — обнаруживает подмену данных
- **Per-user ключ:** компрометация одного пользователя не раскрывает ключи других
- **Не храним пароль как ключ:** PBKDF2 делает brute-force атаку на UEK вычислительно дорогой
- **IV уникален:** каждое шифрование генерирует новый случайный IV — одинаковые ключи дают разный ciphertext

### Что хранится в БД

```sql
api_keys (
  id, user_id, provider,
  encrypted_key TEXT,   -- base64(iv + authTag + ciphertext)
  key_hint TEXT,        -- последние 4 символа для идентификации (sk-...ABCD)
  created_at, updated_at
)
```

### Последствия

- При смене пароля пользователя нужно перешифровать все его ключи
- Если пользователь забудет пароль — ключи невозможно восстановить без него (это особенность, которую нужно объяснить пользователю)
- UEK в памяти сервера — риск при memory dump. Митигация: минимальный TTL кэша, encrypted swap

## ADR-008 — Авторизация через JWT (access + refresh token)

**Дата:** Май 2026  
**Статус:** Accepted

### Контекст

Нужен механизм авторизации, который работает для Web и iOS, stateless (нет серверных сессий), с возможностью отзыва доступа.

### Решение

**Access token** (JWT, 15 минут) + **Refresh token** (opaque, 30 дней, хранится в БД).

```
Логин:
Client  ──▶  POST /auth/login  ──▶  { accessToken, refreshToken }

Запрос:
Client  ──▶  Authorization: Bearer <accessToken>  ──▶  Backend

Обновление:
Client  ──▶  POST /auth/refresh { refreshToken }  ──▶  { новый accessToken }
```

### Детали

- **Access token:** JWT, подписан HS256 с `ACCESS_TOKEN_SECRET`. Содержит `userId`, `email`, `iat`, `exp`. Короткое время жизни — компрометация ограничена 15 минутами.
- **Refresh token:** случайная строка (32 байта, base64url). Хранится в БД с `userId`, `expiresAt`, `revokedAt`. Позволяет отозвать сессию.
- **Web:** access token в памяти (не localStorage), refresh token в `httpOnly Secure` cookie.
- **iOS:** оба токена в Keychain.

### Отклонённые альтернативы

| Альтернатива | Причина отклонения |
|---|---|
| Только один долгоживущий JWT | Нельзя отозвать без проверки по БД — теряется смысл JWT |
| Серверные сессии (session store) | Stateful, требует Redis или sticky sessions, сложнее масштабировать |
| OAuth только (Google/Apple) | Зависимость от сторонних провайдеров, не все пользователи хотят логин через соцсети |

### Последствия

- Refresh token в БД — при каждом обновлении одно обращение к БД
- Rotation стратегия: при использовании refresh token выдаётся новый, старый инвалидируется (защита от кражи токена)
- При обнаружении повторного использования отозванного refresh token — все сессии пользователя инвалидируются

## ADR-009 — React + Zustand для Web-клиента

**Дата:** Май 2026  
**Статус:** Accepted

### Контекст

Выбор технологического стека для Web-клиента. Приложение — SPA с реактивным UI, стримингом, сложным состоянием (чаты, мультимодельный режим, диффы).

### Решение

**React 19 + TypeScript** для UI, **Zustand** для глобального состояния, **TanStack Query** для серверного состояния и кэширования.

### Обоснование

**React:**
- Стандарт индустрии для SPA, огромная экосистема
- React 19 с Server Components не используем (SPA), но новые хуки (`use`, `useOptimistic`) полезны для стриминга
- Команда знает React

**Zustand вместо Redux / Context:**
- Минимальный boilerplate — стор в 10 строк без actions, reducers, selectors
- Не требует Provider-обёртки
- Хорошая производительность из коробки (подписки на slice состояния)
- Поддерживает middleware (persist, devtools)

**TanStack Query для серверного состояния:**
- Кэширование списка чатов, моделей, настроек — не нужно писать вручную
- Автоматический refetch, оптимистичные обновления
- Разделение ответственности: Zustand для UI-состояния, TanStack Query для данных с сервера

### Последствия

- Два источника состояния (Zustand + TanStack Query) требуют чёткого разграничения: что где живёт
- Zustand-стор стриминга нужно проектировать осторожно, чтобы ре-рендеры не тормозили UI при потоке токенов

## ADR-010 — SwiftUI + MVVM для iOS-клиента

**Дата:** Май 2026  
**Статус:** Accepted

### Контекст

Выбор архитектуры iOS-приложения. Нужна поддержка iOS 16+, стриминг, Keychain, iPad-layout.

### Решение

**SwiftUI** для UI, архитектура **MVVM** с `@Observable` (Swift 5.9+), **async/await + URLSession** для сети.

### Обоснование

**SwiftUI:**
- Современный декларативный UI от Apple, активно развивается
- Нативная поддержка iPad (адаптивный layout через `NavigationSplitView`)
- `@Observable` в Swift 5.9 делает MVVM чистым без Combine-цепочек

**MVVM:**
- Чёткое разделение: View (SwiftUI) ↔ ViewModel (`@Observable` class) ↔ Model/Service
- ViewModel тестируемы без UI
- Стандарт для SwiftUI-приложений

**async/await + URLSession для стриминга:**
```swift
// Стриминг SSE нативно через URLSession
let (bytes, _) = try await URLSession.shared.bytes(for: request)
for try await line in bytes.lines {
    // обрабатываем SSE-события
}
```

### Отклонённые альтернативы

| Альтернатива | Причина отклонения |
|---|---|
| UIKit | Устаревший подход для нового приложения, больше boilerplate |
| TCA (The Composable Architecture) | Избыточна для нашей сложности, steep learning curve |
| Combine для сети | async/await читается проще и является современным стандартом |

### Последствия

- `@Observable` требует iOS 17+, для iOS 16 нужен `@ObservableObject` / `@StateObject` — поддержим оба варианта через `#available`
- SwiftUI на iPad требует внимания к layout: `NavigationSplitView` для sidebar + content + detail

## ADR-011 — Мультимодельный режим: параллельные запросы на бэкэнде

**Дата:** Май 2026  
**Статус:** Accepted

### Контекст

В мультимодельном режиме один промпт отправляется 2–4 моделям одновременно. Нужно решить: где запускать параллельные запросы — на клиенте или на бэкэнде?

### Решение

Параллельные запросы запускаются **на бэкэнде**. Клиент отправляет один запрос на `/proxy/multi`, бэкэнд запускает N параллельных запросов к провайдерам и мультиплексирует стримы в один SSE-поток.

```
Client  ──▶  POST /proxy/multi { models: [...], messages: [...] }
                       │
              Node.js Backend
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
    OpenAI API    Anthropic API   Gemini API
        │              │              │
        └──────────────┼──────────────┘
                       ▼
              Мультиплексированный SSE стрим
              { modelId, delta, ... }
                       │
                    Client
```

### Формат SSE событий

```
event: chunk
data: {"modelId": "gpt-4o", "delta": "Привет", "index": 0}

event: chunk
data: {"modelId": "claude-sonnet-4", "delta": "Здравствуйте", "index": 0}

event: done
data: {"modelId": "gpt-4o", "usage": {"promptTokens": 10, "completionTokens": 42}}
```

### Обоснование

- **Один SSE-поток вместо N:** клиенту не нужно управлять несколькими соединениями — упрощает логику, особенно на iOS
- **Обход CORS:** из браузера нельзя надёжно параллельно открыть 4 SSE-соединения к разным доменам
- **Централизованное управление:** тайм-ауты, retry, rate limiting — всё на бэкэнде
- **`Promise.allSettled`:** падение одного провайдера не останавливает остальных

### Последствия

- Бэкэнд держит N одновременных исходящих соединений к провайдерам — нужно следить за лимитами keep-alive
- Клиент должен корректно обрабатывать частичный failure (одна модель упала, остальные работают)

## ADR-012 — Дифф-просмотр файлов только на Web в v1

**Дата:** Май 2026  
**Статус:** Accepted

### Контекст

Одна из ключевых функций — работа с файлами и визуализация изменений (диффов). Нужно решить, реализовывать ли её сразу на обеих платформах.

### Решение

В v1 дифф-просмотр реализуется **только на Web**. На iOS — в дорожной карте (v1.x).

### Обоснование

- **Экосистема Web:** зрелые библиотеки для диффов (Monaco Editor, diff2html, CodeMirror) — реализация занимает дни, а не недели
- **Типичный usecase:** работа с кодом и файлами происходит за десктопом, а не на телефоне
- **Фокус:** лучше сделать одну платформу отлично, чем две посредственно
- **iOS сложнее:** нативный split-view дифф на iOS требует кастомного рендерера — значительные трудозатраты

### Технологический выбор для Web

**Monaco Editor** (тот же редактор, что в VS Code):
- Встроенный diff viewer (`createDiffEditor`)
- Подсветка синтаксиса для 50+ языков
- Принятие/отклонение изменений — нужно реализовать поверх
- Размер бандла: ~2 МБ (грузится лениво)

### Последствия

- Пользователи iOS не имеют доступа к дифф-функции в v1 — нужно чётко коммуницировать это в App Store
- При реализации на iOS: рассмотреть `WKWebView` с тем же Monaco (компромисс нативность vs скорость разработки)
